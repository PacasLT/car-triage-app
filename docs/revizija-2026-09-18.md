## 1. RIMTA · Duomenys kaupiami be jokios ribos

`cache.js` laiko tris JSON failus `/data` kataloge. Du iš jų **niekada nieko netrina**:

| Failas | Ribojimas | Auga pagal |
|---|---|---|
| `market-history.json` | **1000 įrašų modeliui** ✓ | modelių skaičių |
| `listing-lifecycle.json` | **jokio** ✗ | kiekvieną kada nors matytą skelbimą |
| `listing-timeline.json` | 60 momentinių vaizdų vienam URL, bet **URL niekada netrinami** ✗ | kiekvieną kada nors matytą skelbimą |

Visi trys **pilnai įkeliami į atmintį paleidžiant** (`JSON.parse`) ir **pilnai perrašomi** kiekvieno išsaugojimo metu.

Skaičiavimas: vienas `lifecycle` įrašas ≈ 300 B, vienas `timeline` URL ≈ 60 B – 1,8 KB.
Jei per parą pamatoma 900 naujų skelbimų, po metų tai ≈ **330 000 įrašų ≈ 100 MB + iki 500 MB**.

Tai **tas pats gedimas, kuris jau buvo** — `cache.js` komentaruose aprašyta, kaip `pages` erdvė išaugino `cache.json` iki šimtų MB ir Railway konteineris krito iš atminties. Tada sprendimas buvo išimti HTML iš failo. Dabar ta pati spraga liko dviejuose kituose failuose.

**Sprendimas:** riba pagal amžių. Skelbimas, kurio `paskutinMatytas` senesnis nei ~180 d. ir kuris pažymėtas `dingo`, nieko nebepasako — jis tik užima atmintį. Valymas paleidžiant ir kartą per parą.

## 2. RIMTA · Kiekvienas skelbimas perrašo visą failą

`cache.js:222` — `recordListingSnapshot()` baigiasi `saveListingTimeline()`, o tai yra
`JSON.stringify` visam failui + **sinchroninis** `writeFileSync`.

`server.js:2016` kviečia jį **cikle kiekvienam skelbimui**:

```js
visiMatyti.forEach((l) => {
  cache.zymetiMatyta(l, {...});
  if (l.kaina) cache.recordListingSnapshot(l.url, l.kaina, l.rida || null);
});
cache.saveLifecycle();   // <- šitas teisingai: vieną kartą, su dirty vėliava
```

Prie 60–100 skelbimų per paiešką tai **60–100 pilnų sinchroninių įrašymų**. Kol jie vyksta, Node nieko kito nedaro — serveris neatsako į jokią kitą užklausą.

Vėlgi: `setCached` komentaruose jau aprašyta **ta pati klaida** („~86 rašymai po keliasdešimt MB — serveris tuo metu neatsakydavo į jokias kitas užklausas, progreso juosta atrodydavo užšalusi"). `saveLifecycle` ją išsprendė dirty vėliava. `saveListingTimeline` liko nepataisytas.

**Sprendimas:** ta pati dirty vėliava, kaip `saveLifecycle`. Vienos eilutės pakeitimas `recordListingSnapshot` viduje plius `saveListingTimeline()` po ciklo.

## 6. Saugumas: kas patikrinta ir kas rasta

### Švaru ✓

**Svetimų duomenų prieiga (IDOR) — nėra.** Visos užklausos `vartotojo-duomenys.js` yra apribotos `user_id`:

```js
db.prepare('SELECT * FROM ataskaitos WHERE user_id = ? AND id = ?').get(userId, id)
db.prepare('DELETE FROM ataskaitos WHERE user_id = ? AND id = ?').run(userId, id)
```

Pakeitus `id` URL'e svetima ataskaita negrįžta.

**SQL injekcijos nėra.** Visur `db.prepare(...)` su parametrais.

**Kreditų klientas paveikti negali.** Kainos gyvena serveryje (`planai.js` `KAINOS`), maršrutas pats pasako veiksmo pavadinimą. Klientas kiekio nesiunčia.

**XSS per URL — patikrinta naršyklėje, neaptikta.** Paleidau visus penkis puslapius su kenksmingu kroviniu (`"><img src=x onerror=...>`) trylikoje parametrų. Nė viename nepateko į `innerHTML`, žymė neatsirado, `window.__xss` neuždėtas. `marke` yra `<select>`, o `updateGenerationHint()` piešia tik tada, kai pora randama `GENERATION_INFO` lentelėje — nežinomas tekstas iškrenta anksčiau.

**JWT konfigūracija tvarkinga.** 72 val. galiojimas, paslaptis iš env, trumpesnė nei 32 simboliai — garsus įspėjimas į konsolę, o ne tylus atsarginis raktas.

### Verta sutvarkyti

**a) `INVITE_CODES` turi viešą atsarginę reikšmę.**
`auth.js:41` — `process.env.INVITE_CODES || 'CARTRIAGE2024'`. Jei Railway kintamasis kada nors dingtų, registracija atsivertų bet kam, kas skaitė šitą kodą GitHub'e. Geriau: nėra kintamojo → registracija uždaryta.

**b) `jwt.verify` be `algorithms`.**
`auth.js:105` — verta prirašyti `{ algorithms: ['HS256'] }`. Šiandien tai nieko nekeičia, bet tai vienos eilutės apsauga nuo klaidos ateityje.

**c) Kreditų nurašymas saugus TIK todėl, kad tarp skaitymo ir rašymo nėra `await`.**

```js
const u = gautiVartotoja(userId);          // skaitymas
let plano = ..., pirkti = ...;             // skaičiavimas
db.prepare('UPDATE users SET ...').run();  // rašymas
```

`better-sqlite3` sinchroninis, Node vienagijis — tarp šitų eilučių niekas kitas neįsiterpia. Bet jei kas nors kada nors įdės `await` (pvz. logą į išorinę sistemą), atsiras dviguba nurašymo spraga, ir ji bus nematoma. **Verta apvilkti `db.transaction()`** — tada saugumas nebepriklausys nuo to, ar kažkas neįdėjo `await`.

## 10. Dvi įžvalgos, kurios ne apie klaidas

**Pirma: tos pačios klaidos kartojasi skirtinguose failuose.**
Sinchroninis pilno failo perrašymas cikle buvo rastas ir ištaisytas `setCached`. Ta pati klaida liko `saveListingTimeline`. Neribotas augimas buvo rastas ir ištaisytas `pages`. Ta pati spraga liko `lifecycle` ir `timeline`. Rožinė spalva buvo taisoma keturis kartus, o ji gyveno **22 vietose**.

Tai ne neatidumas — tai ženklas, kad taisoma ta vieta, kuri skauda, o ne visos vienodos vietos. Kai kitą kartą kas nors pasitaiso, verta iškart paklausti: **„kur dar yra tas pats?"** Ta pati praktika, kuri dizaine davė 28 → 24.

**Antra: sistema saugo daugiau, nei naudoja.**
`listing-timeline` laiko 60 momentinių vaizdų vienam skelbimui, o `buildListingTimelineText` naudoja **tris**: pirmą, priešpaskutinį ir paskutinį. Likę 57 niekada neperskaitomi — tik įkeliami, perrašomi ir užima atmintį.

Tai nėra vien atliekos: kaupti verta tada, kai žinai, ką iš to skaičiuosi. Jei 60 taškų reikia kainos kreivei — tada reikia ir kreivės. Jei nereikia, užtenka trijų. **Verta apsispręsti, o ne kaupti „dėl visa ko".**
